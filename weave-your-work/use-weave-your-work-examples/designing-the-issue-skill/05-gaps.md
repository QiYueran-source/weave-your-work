# What this example does not show

- **Any host other than GitHub.** GitHub's five actions were run end to end on a private scratch repository on 2026-11-08; the probe issue is closed and the repository is archived. Gitee's create, comment, and close were deferred by the user on 2026-11-08, and its reference was deleted on 2026-11-09 along with the GitHub one; the reads and endpoints were checked, and a Gitee write has still not run. On 2026-11-09 the skill was narrowed to GitHub, so a Gitee write is no longer a gap in this skill: it is work for a fork.
- **A listener for a host other than GitHub.** The listener reads GitHub's webhook payload and lists issues with `gh api`; the two functions that do this are marked in the file and listed in `usage.md`. No second host has been written, so the seam is described but not exercised. Nothing depends on it, because the skill no longer claims a second host is a configuration away.
- **A blind read of the skill.** Four fresh readers, each given only the three files and the caller's design ticket, walked the archive, human-step, foreign-parent, and outside-proposal cases; all four could execute it. They found the boundary gaps the rules now answer: who names the recipient and what happens without a handle or account, who gives the public-repo yes when the repository is not the run's, where the receipt lives when no replacement exists or the continuing ticket is foreign, how a closed thread with the same id is found, the command for a status change, how a proposal with no ticket is found and judged, where its new ticket's source goes, how a decline closes, and the fact that nothing watches a thread. Four readers match the update skill's build; each read one case. A fifth re-read the proposal case after the triage and handle rules landed; it found three more boundary gaps — which map judges a proposal with no local ticket, what the closing comment names when there is no ticket, and who writes the `Out of scope` line when the judge is not the run's owner. The rules now answer each. A sixth re-read the archive case with the roster and found one ambiguity — which id the title carries when the answer and the receipt sit on different tickets — now spelled out.
- **A real cross-owner hand-over.** Every ticket in this repository is owned by `frank`, so the archive example in [Three callers and one message](01-three-callers.md) is a scenario, not a run. The shape is checked against the update map's rule; the delivery is not.
- **Authentication.** The listener queues an issue only when its author is a login in `handles.toml`, which stops a stranger on a public repository. It is a roster, not a signature: smee parses and re-serializes the body, so GitHub's HMAC over the original bytes never matches, and the author field rides in the same unverified payload. Anyone who knows the channel URL can post any login. Real verification needs a tunnel with `WEBHOOK_SECRET` set, which is not built.
- **The `comment` category's fate.** The skill uses it as a remote message category, but the local Waymark `comment` category is still declared and the glossary still defines it. Whether the local one stays is a decision for the execution map, which owns the question.
- **The end-to-end batch.** The root map runs every skill's paths once the set is whole. This example records the design of one skill; it is not that test, and it does not claim the issue skill works beside the others.
