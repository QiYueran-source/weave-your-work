# What this example does not show

- **A retire-and-replace run on a real node.** The seven-step order in `content.md` was run end to end in a scratch project on 2026-11-08 — a map with two children and a foreign dependent — and held: `validate` clean, the surviving child under the replacement, the dependent `blocked` → `ready`, the dry-run naming exactly the ticket the archive would edit. No node in this repository has been through it, so the order has still not met a real review verdict or a real issue.
- **The order correction that came out of that run.** The steps first said to clear the parent field on the holder. It is the child that carries it: archiving a child while it still points at its parent breaks `validate` the moment the parent is archived, and an archived child rejects the clear afterwards. There is no unarchive command; the only repair is editing the archived file by hand.
- **A cross-owner write.** Every one of the 52 ticket files is owned by `frank`, so the notify-afterwards rule has never run on a real foreign ticket. It was checked in a scratch project with three owners, where the dry-run's silence about the foreign tickets was confirmed. The issue it depends on belongs to [the communication map](../../../tickets/map/wm-25b3q7mg88c7.md), which is still in design.
- **The skill's own usability, read by someone with no context.** Three fresh readers were given only the three files and three real tickets. The first could not execute the skill at all: the second test needed a verdict and the skill never said where one lives, it asserted a `## Review` section that 11 of the 15 closed tasks here do not have, it admitted open split maps and then applied a closed-only disposition to them, it named five relations in the scan and no command that reads them, and it filed "a fact that was always wrong" as editorial while its own act-differently test says otherwise. The second found the pieces the fixes broke or under-specified: `waymark create --parent` is not a runnable command, `waymark search` reads the ticket store and not the files, and one paragraph said a map's `needs changes` verdict lands in `Decisions so far` while another said a map writes nothing. The third is not recorded here.
- **Why the readers were needed at all.** Every earlier check asked whether the skill's claims about waymark were true, and they were. None asked whether a person holding the skill could act on it, and on the first try one could not. Checking the facts and checking the use are two different tests, and only the second one caught this.
- **A split map whose content changed through the skill.** Still no worked example.
