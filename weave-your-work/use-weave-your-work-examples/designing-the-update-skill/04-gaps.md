# What this example does not show

- **A retire-and-replace run on a real node.** The seven-step order in `content.md` was run end to end in a scratch project on 2026-11-08 — a map with two children and a foreign dependent — and held: `validate` clean, the surviving child under the replacement, the dependent `blocked` → `ready`, the dry-run naming exactly the ticket the archive would edit. No node in this repository has been through it, so the order has still not met a real review verdict or a real issue.
- **The order correction that came out of that run.** The steps first said to clear the parent field on the holder. It is the child that carries it: archiving a child while it still points at its parent breaks `validate` the moment the parent is archived, and an archived child rejects the clear afterwards. There is no unarchive command; the only repair is editing the archived file by hand.
- **A cross-owner write, on a real repository ticket.** The write itself was exercised in a scratch project with three owners: a node owned by one person archived while a ticket owned by another depended on it. The dependent's file lost its `dependencies:` block, the dependent went `blocked` → `ready`, and `OWNER_MISMATCH` appeared only for the owner of the archived node. So the mechanism is checked. What has not happened is the step after it — no issue has ever been filed, because every one of this repository's 52 ticket files is owned by `frank` and the issue shape belongs to [the communication map](../../../tickets/map/wm-25b3q7mg88c7.md), which is still in design.
- **The skill's own usability, read by someone with no context.** Four fresh readers were given only the three files and three real tickets. The first could not execute the skill at all: the second test needed a verdict and the skill never said where one lives, it asserted a `## Review` section that 11 of the 15 closed tasks here do not have, it admitted open split maps and then applied a closed-only disposition to them, it named five relations in the scan and no command that reads them, and it filed "a fact that was always wrong" as editorial while its own act-differently test says otherwise. The second found the pieces the fixes broke or under-specified: `waymark create --parent` is not a runnable command, `waymark search` reads the ticket store and not the files, and one paragraph said a map's `needs changes` verdict lands in `Decisions so far` while another said a map writes nothing. The third called the skill usable and found the last real defect: the skill defined a map's verdict two ways at once — the acceptance direction to read, and a status that was the only place a verdict showed — so on a closed map the second test could never fail. It also caught that my own fix to the `--json list` claim was wrong: `parent` and `soft_links` are there, nested under `item`. Three readers, three rounds. A fourth checked the third's fix and found the section still used one word for two things — a map's acceptance direction as its verdict, and as not-a-verdict — which is now split into a plan and a kept promise. Four rounds is where it stopped, and the reason is that the fourth was finding wording rather than missing steps. That is a judgement, not a measurement: a fifth reader might still find something.
- **Why the readers were needed at all.** Every earlier check asked whether the skill's claims about waymark were true, and they were. None asked whether a person holding the skill could act on it, and on the first try one could not. Checking the facts and checking the use are two different tests, and only the second one caught this.
- **A split map whose content changed through the skill.** Still no worked example.
