# What this example does not show

- **A retire-and-replace run on a real node.** The seven-step order in `content.md` was run end to end in a scratch project on 2026-11-08 — a map with two children and a foreign dependent — and held: `validate` clean, the surviving child under the replacement, the dependent `blocked` → `ready`, the dry-run naming exactly the ticket the archive would edit. No node in this repository has been through it, so the order has still not met a real review verdict or a real issue.
- **The order correction that came out of that run.** The steps first said to clear the parent field on the holder. It is the child that carries it: archiving a child while it still points at its parent breaks `validate` the moment the parent is archived, and an archived child rejects the clear afterwards. There is no unarchive command; the only repair is editing the archived file by hand.
- **A cross-owner write.** Every one of the 51 ticket files is owned by `frank`, so the notify-afterwards rule has never run on a real foreign ticket. It was checked in a scratch project with three owners, where the dry-run's silence about the foreign tickets was confirmed. The issue it depends on belongs to [the communication map](../../../tickets/map/wm-25b3q7mg88c7.md), which is still in design.
- **A split map whose content changed.** The update skill's second trigger — a map that has already split but is still open — is stated in the design and has no worked example behind it.
