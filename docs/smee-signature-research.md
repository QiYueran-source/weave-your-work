# Smee.io and GitHub webhook signatures

## Findings

GitHub computes `X-Hub-Signature-256` as an HMAC-SHA256 over the payload contents using the configured webhook secret. Verification must use the received body bytes before parsing or other processing; GitHub specifically warns that a proxy or load balancer must not modify payloads or headers before verification. Use constant-time comparison. [GitHub: Validating webhook deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)

The published `probot/smee.io` server implementation does not preserve the original raw request body in its event structure. Fastify parses the POST body as an object (`body: { type: 'object' }`); the handler emits an event containing `req.body`, headers and query parameters. The SSE response serializes the event object to JSON (unless Redis is enabled, where the event is serialized before publishing). The published `probot/smee-client` then parses SSE JSON, extracts `data.body`, and runs `JSON.stringify(data.body)` to create the downstream HTTP body. Therefore the published implementation documents a parse-and-reserialize path, not byte-for-byte preservation. JSON serialization can change whitespace, key order, escaping, or number representation from the bytes GitHub originally signed. [smee.io server source](https://github.com/probot/smee.io/blob/922d925bc241c2e40a1ec86da631b3dbbdd329cb/lib/server.js) · [smee.io event bus source](https://github.com/probot/smee.io/blob/922d925bc241c2e40a1ec86da631b3dbbdd329cb/lib/event-bus.js) · [installed smee-client](../.agents/skills/issue/bundle/tools/node_modules/smee-client/index.js)

The published server's `POST /:channel` handler awaits `bus.emit(...)` and then returns HTTP 200. This is not an acknowledgment from a downstream local listener: the code does not await that listener's HTTP response or signature verification. The bus returns an EventEmitter result when Redis is not enabled; the server does not use that result when deciding its 200 response. Thus a GitHub-visible 200 from this upstream handler does not establish that the local receiver accepted, verified, or even received the forwarded event. [smee.io server source](https://github.com/probot/smee.io/blob/922d925bc241c2e40a1ec86da631b3dbbdd329cb/lib/server.js) · [smee.io event bus source](https://github.com/probot/smee.io/blob/922d925bc241c2e40a1ec86da631b3dbbdd329cb/lib/event-bus.js)

Smee's maintainers state that smee.io is intended for development, not production. Channels are not authenticated; anyone who knows the channel ID can see payloads, and only actively connected clients receive them. [smee.io README](https://github.com/probot/smee.io/blob/922d925bc241c2e40a1ec86da631b3dbbdd329cb/README.md)

GitHub does not automatically retry failed webhook deliveries; a failed delivery can be manually redelivered. A 200 at Smee's ingress is therefore especially distinct from successful processing at a forwarded local listener. [GitHub: Handling failed webhook deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)

## Evidence limits and local observations

These source-level findings describe the published upstream repository, not a measurement of the currently deployed `smee.io` service. No live webhook, channel, or public payload was sent or inspected for this note. Live deployed behavior, including whether it matches the current upstream revision or deployment configuration, remains unverified.

A local regression test already recorded in this repository covers signed-body verification with a reserialized JSON body and split UTF-8 input. On 2026-11-09, `node --test --test-name-pattern='original bytes' .agents/skills/issue/bundle/tools/test-security.mjs` passed the matching test using simulated reserialization and a local HTTP server only. This is local evidence; it does not test the live Smee service. [Local security test](../.agents/skills/issue/bundle/tools/test-security.mjs)

## Alternatives to test

A reverse proxy or tunnel can forward a public HTTPS webhook to the existing listener, which already supports running without `SMEE_URL` and verifies bytes before parsing. GitHub describes reverse proxies for private systems and recommends restricting inbound traffic and verifying signatures. [GitHub: Delivering webhooks to private systems](https://docs.github.com/en/webhooks/using-webhooks/delivering-webhooks-to-private-systems) · [listener](../weave-your-work/issue/bundle/tools/listener.mjs)

- [Cloudflare Quick Tunnel](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/) needs no account or domain, but is for testing only: the hostname changes on creation, there is no uptime guarantee, and it stops when the process stops. A [named tunnel](https://developers.cloudflare.com/tunnel/get-started/) for a stable hostname requires an account and a domain on Cloudflare.
- [ngrok](https://ngrok.com/docs/share-localhost/webhooks/) supports forwarding webhooks to a local service; its [quickstart](https://ngrok.com/docs/share-localhost/quickstart/) requires an account and token, and its [free plan](https://ngrok.com/docs/pricing-limits/free-plan-limits/) has limits.
- An owned public server with an HTTPS reverse proxy and SSH remote forwarding is another option, but requires administration of the server, DNS, TLS, and a persistent SSH connection. [OpenSSH manual](https://man.openbsd.org/ssh.1#R)

None of these candidates has been tested here for body or signature-header preservation. Neither `cloudflared` nor `ngrok` was installed or available on PATH during this investigation. Before selecting a solution, send a signed test payload containing whitespace, Unicode and escapes through the actual public endpoint; compare the bytes and headers received and verify that valid signatures pass and modified or missing signatures fail. Then test an actual GitHub delivery separately. Address stability and outage recovery are separate tests. A search for open mentions is not a complete replay of all missed events.
