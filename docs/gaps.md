# Gaps: paths the skills have not exercised

Each skill records the paths it was designed for but never ran. The lists below were written inside the worked examples, one per skill, and were merged into this file on 2026-11-10 when those pages were deleted. Nothing here is closed by being written down: an item stays until a run exercises it or a decision removes the path, and the one item that has since been decided says so.

The point of the file is the end-to-end batch the root map describes: once the skill set is whole, every skill's paths are walked once and whatever the walk shows is fixed. These lists are that batch's input. The last two sections are not gaps in a skill: one records what has been settled since, the other records what a reader test is for and what it has caught.

## Update skill

- **A retire-and-replace run on a real node.** The seven-step order in `content.md` was run end to end in a scratch project on 2026-11-08 — a map with two children and a foreign dependent — and held: `validate` clean, the surviving child under the replacement, the dependent `blocked` → `ready`, the dry-run naming exactly the ticket the archive would edit. No node in this repository has been through it, so the order has still not met a real review verdict or a real issue.
- **The order correction that came out of that run.** The steps first said to clear the parent field on the holder. It is the child that carries it: archiving a child while it still points at its parent breaks `validate` the moment the parent is archived, and an archived child rejects the clear afterwards. There is no unarchive command; the only repair is editing the archived file by hand.
- **A cross-owner write, on a real repository ticket.** The write itself was exercised in a scratch project with three owners: a node owned by one person archived while a ticket owned by another depended on it. The dependent's file lost its `dependencies:` block, the dependent went `blocked` → `ready`, and `OWNER_MISMATCH` appeared only for the owner of the archived node. So the mechanism is checked. What has not happened is the step after it — no issue has ever been filed for it by this skill.
- **A split map whose content changed through the skill.** Still no worked example. The batch in the `data-analysis/` example covers an editorial edit, an invalidated verdict, a replaced subject, and a move, but not a map whose acceptance direction is edited while its children are live.

## Issue skill

- **Any host other than GitHub.** GitHub's five actions were run end to end on a private scratch repository on 2026-11-08; the probe issue is closed and the repository is archived. Gitee's create, comment, and close were deferred by the user on 2026-11-08, and its reference was deleted on 2026-11-09 along with the GitHub one. On 2026-11-09 the skill was narrowed to GitHub, so a Gitee write is no longer a gap in this skill: it is work for a fork. The API differences a fork would hit are in [Gitee API notes](gitee-api-notes.md).
- **A listener for a host other than GitHub.** The listener reads GitHub's webhook payload and lists issues with `gh api`; the two functions that do this are marked in the file and listed in `usage.md`. No second host has been written, so the seam is described but not exercised. Nothing depends on it, because the skill no longer claims a second host is a configuration away.
- **The setup path on a repository that already has a listener.** The steps read the channel and webhook back with `gh` and create only when the read is empty, but they have only been run as a first install. Re-installing over a live listener is described, not exercised.
- **A real cross-owner hand-over, two machines apart.** Run on 2026-11-09 in both directions between `QiYueran-source` and a second account, from two clones on one machine; the listener's routing was checked against two queues rather than one. Two machines, a real second person, and the session-start rule are still unexercised. Every ticket in this repository is owned by `frank`, so a ticket actually changing owner is also unverified.
- **Authentication.** The listener queues an issue only when its author is a login in `handles.toml`, which stops a stranger on a public repository. It is a roster, not a signature: smee parses and re-serializes the body, so GitHub's HMAC over the original bytes never matches, and the author field rides in the same unverified payload. Anyone who knows the channel URL can post any login. Real verification needs a tunnel with `WEBHOOK_SECRET` set, which is not built.
- **The end-to-end batch.** The root map runs every skill's paths once the set is whole. Neither list on this page is that test.

## The reader test

Every earlier check of these two skills asked whether their claims about `waymark` and `gh` were true, and they were. None asked whether a person holding the skill could act on it, and on the first try one could not. **Checking the facts and checking the use are two different tests, and only the second one caught anything.**

What the rounds found, kept here because the rules they produced are scattered across both skills and the rounds themselves are recorded nowhere else:

- **Update, four rounds.** The first reader could not execute the skill at all: the second test needed a verdict and the skill never said where one lives, it asserted a `## Review` section that 11 of the 15 closed tasks here do not have, it admitted open split maps and then applied a closed-only disposition to them, it named five relations in the scan and no command that reads them, and it filed "a fact that was always wrong" as editorial while its own act-differently test said otherwise. The second found what the fixes broke: `waymark create --parent` was described as a runnable command, `waymark search` reads the ticket store rather than the files, and one paragraph put a map's `needs changes` verdict in `Decisions so far` while another said a map writes nothing. The third called the skill usable and found a definition used twice — a map's verdict as the acceptance direction to read, and as a status that was the only place a verdict showed — so on a closed map the second test could never fail. A fourth checked the third's fix and found one word still doing two jobs, now split into a plan and a kept promise. It stopped there because the fourth was finding wording rather than missing steps; that is a judgement, not a measurement.
- **Issue, six rounds.** Four readers walked the archive, human-step, foreign-parent, and outside-proposal cases and all four could execute the skill; they found the boundary gaps the rules now answer — who names the recipient and what happens without a handle or account, who gives the public-repo yes when the repository is not the run's, where the receipt lives when there is no replacement or the continuing ticket is foreign, how a closed thread with the same id is found, the command for a status change, how a proposal with no ticket is found and judged, where its new ticket's source goes, how a decline closes, and that nothing watches a thread. A fifth re-read the proposal case after the triage and handle rules landed and found three more: which map judges a proposal with no local ticket, what the closing comment names when there is no ticket, and who writes the `Out of scope` line when the judge is not the run's owner. A sixth re-read the archive case with the roster and found one ambiguity: which id the title carries when the answer and the receipt sit on different tickets.

The cost is worth stating as plainly as the benefit: a reader round needs a scratch project and an agent with no context, and four to six of them were run per skill. The alternative is a skill that is factually correct and unusable, which is what both of these were before the rounds.
