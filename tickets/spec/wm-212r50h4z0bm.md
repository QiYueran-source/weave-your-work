## Problem Statement

The communicate-with-issue skill and the queue behind it no longer describe
what a person actually does.

**The queue records one direction.** `queueIssue` in `listener.mjs` rejects
every issue whose assignee is not this machine's owner (line 503). A person who
opens an issue and assigns it to another owner gets nothing in their own queue,
so they have no local signal about whether the other side has handled it. The
recipient's session is reminded; the sender's is not.

**The skill defined a contract the two checkouts cannot keep.** The format file
said `tickets[0]` is the main record, the title carries it, and the answer lands
there. A `wm-` id names a file in the sender's `tickets/` directory. The
recipient does not have it, cannot read it, and has no shared tracker to write
to. `RECEIVE.md` instructed the recipient to write that record, which is not
possible across an issue.

**The skill was organised around state management that does not exist.**
`RECEIVE.md` was a list of three behaviours with done conditions, all of them
about landing an answer on a record the recipient cannot reach. `SEND.md`
carried the only `gh` commands and the failure branches. Splitting send from
receive forced every run to decide which half it was in before it could find
the command it needed.

**The session rule forbade the thing it was for.** `rules-pending-
communications.md` step 3 said "Do not act on an entry until the person asks",
while the queue's own contract was that a line stays until its issue closes. An
unanswered issue returned every session.

**The rule had no source.** `install-issue.md` copies
`rules/rules-pending-communications.md` from the setup skill. No such file
existed there.

The user's decisions, in their words:

- A message should be handled by whoever receives it until it closes, using
  `gh` directly for comments and changes; the queue only records creation.
- Remove the record-management rules: an id pointing at a file the other
  machine does not have cannot be acted on. Content is the message.
- Keep only `SKILL.md` and the format file in the skill.
- The session rule should say that pending messages are handled promptly and
  closed, not that they wait for a person to ask.
- Only the account that opened an issue closes it. A recipient who has settled
  the ask replies and mentions the sender so they close it.

## Solution

**One skill file, one format file.** `SKILL.md` carries the whole flow: what a
message is, how to send one, how to answer one, what to do when a step fails,
and what the queue holds. `COMMUNICATE-ISSUE-FORMAT.md` defines the record:
front matter, who is speaking, title and body, the thread, and what the queue
records. `SEND.md` and `RECEIVE.md` are deleted; their still-useful content
moves into `SKILL.md`, and their record-management content is dropped.

**The queue records both directions.** An issue is queued when either its
author or its assignee is this machine's owner. One line per open issue, added
when the issue is opened, carrying only what was true then. Comments are not in
it. The line stays until the issue closes.

**Closing does not move.** Only the issue's author closes it. The listener
still refuses a close by anyone else, and the startup scan still marks a line
whose issue GitHub no longer lists as open. A recipient who has settled the ask
replies and mentions the sender.

**The record's id claim goes.** The title no longer carries a record id,
`tickets` no longer names a landing place, and nothing promises that an answer
lands on a record. A message that is about a record says so in its body, in
prose, for a reader. The front matter keeps `kind` and `category`: `kind` marks
the issue for the listener, and `category` says whether the message asks for
work, reports a result, or adds to a thread.

**The rule says what to do.** Read the queue, work through the open threads,
use `gh` for the thread because the queue line does not hold it, close what this
machine's owner opened, and reply-and-mention for what someone else opened.

## User Stories

1. As a person who sends an issue to another owner, I want it in my own queue
   until it closes, so that I can see whether the other side has handled it
   without opening GitHub.
2. As a person who receives an issue, I want it in my queue as before, so that
   nothing about receiving changes.
3. As a person reading the queue at session start, I want one list of
   everything open that involves me, so that I do not have to look in two
   places.
4. As a person who closed an issue I sent, I want its line marked and gone
   from the report, so that the list stays about work still outstanding.
5. As the owner of a repository with strangers in it, I want an issue that
   neither I sent nor am assigned to to stay out of my queue, so that widening
   the rule does not turn the queue into every issue in the project.
6. As an agent reading the skill, I want the command for the step I am on in
   the file I am reading, so that I do not have to decide which half of the
   skill I am in before I find it.
7. As an agent answering a message, I want to know that the answer goes in the
   thread and not on a file the sender owns, so that I do not look for a record
   I cannot reach.
8. As a person receiving a message, I want to know that I cannot close it, so
   that I reply and mention the sender instead of failing at `gh issue close`.
9. As a person starting a session, I want the rule to say what to do with an
   open thread, so that a queued issue is not left for a person to ask about.
10. As a person maintaining the set, I want the rule to exist in the setup
    skill, so that the install guide's copy step finds the file.

## Implementation Decisions

**The skill keeps two files.** `SKILL.md` and `COMMUNICATE-ISSUE-FORMAT.md`.
`SEND.md` and `RECEIVE.md` are deleted.

**What moves from `SEND.md` into `SKILL.md`:** the five steps (pick the
recipient, write the title and body, open the issue, confirm it exists), the
exact `gh issue create` and `gh issue view` command shapes, the `gh issue edit
--add-assignee` repair, and the failure branches. The failure branch about a
record id naming nothing is dropped with the id claim; the others stay.

**What moves from `RECEIVE.md` into the format file:** a reply is a comment on
the same issue and never a second issue; a message that is not for this machine
stays on GitHub, unqueued, unreplied, unclosed.

**What is dropped from `RECEIVE.md`:** the three behaviours with their done
conditions, the landing instruction, and the "record's owner writes it" rule.
All of it exists to move an answer onto a record the recipient cannot reach.

**The front matter keeps `kind` and `category`.** `kind: communicate` marks the
issue for the listener. `category` is `request`, `result`, or `comment`.
Removing either is a separate decision and is not made here; `tickets` is
removed from the format, the skill, and the listener.

**The title is the point, with no id prefix.** `Title: <the point>`, not
`[<main record id>] <the point>`. A message about a record names it in the
body.

**The queue line does not change shape.** `url`, `from`, `to`, `owner`,
`title`, `received`, `closed_at` stay. `owner` continues to hold the assignee's
owner name.

**One predicate replaces one comparison.** `queueIssue` becomes `const
involved = from === machineOwner || to === machineOwner`, and the skip message
names both owners: `Skipped <label>: <from> to <to> does not involve
<machineOwner>`.

**The startup log says what the listener now does.** `queueing messages
assigned to <owner>` becomes `queueing issues involving <owner>`.

**The report does not gain a direction.** A sent and a received issue look
alike in `check-pending.mjs`'s output. The person reads the queue for "what is
open that I am part of" and opens the issue on GitHub for anything more.

**The roster still gates both sides.** An issue whose author or assignee is
outside the roster is still dropped. Widening the predicate widens which roster
members count, never whether the roster counts.

**The rule lives in the setup skill.** Its source is
`setup/rules/rules-pending-communications.md`, which is what
`install-issue.md` already copies. The project copy at
`.agents/rules/rules-pending-communications.md` is refreshed from it and stays
byte-identical.

**The rule says what to do, not what not to do.** It opens the session with the
open threads, reads each thread with `gh issue view --comments`, replies with
`gh issue comment --body-file`, closes what this machine's owner opened, and
replies-and-mentions for what someone else opened.

**The listener copy installed in a checkout is not edited in place.** It is
reinstalled from the install guide.

## Testing Decisions

**What a good test is here.** The existing shape for the listener: a real
listener against a temporary checkout, an event over HTTP, and the queue file
read back. The fake `gh` on `PATH` answers the single-issue read as it already
does.

**The documentation has no automated test.** Its check is a read: the skill
folder holds two files, `SEND.md` and `RECEIVE.md` are gone, the format file no
longer promises a landing place, and the rule file exists in both the setup
skill and the project.

**What the listener tests cover.**

- An issue this machine's owner opened and assigned to another roster member
  queues one line, with `from` this owner and `to` the other.
- An issue assigned to this machine's owner queues as before.
- An issue whose author and assignee are both other roster members adds no
  line.
- An issue from outside the roster still adds no line, whichever end the
  stranger is on.
- An issue whose front matter carries no `tickets` queues, because `tickets`
  is no longer required.
- The startup scan queues an open issue the owner sent and the queue lacks.
- A line for an issue the owner sent is marked closed by the scan when GitHub
  no longer lists it open, and the listener's own close event still refuses a
  closer who is not the author.

**What changes in the existing tests.** `test-catchup.mjs:290` asserts that an
issue assigned to bob is not queued on alice's machine. The assertion narrows
to "an issue whose two parties are other members is not queued", and a case for
alice's own outgoing issue is added beside it. `test-security.mjs:543` keeps its
stranger case and gains the outgoing case. Every fixture that builds a message
body drops `tickets` from the front matter, and the case asserting "no tickets"
is removed because the field no longer exists.

## Acceptance

A person can see the queue work by opening an issue as their own account,
assigning it to another roster member, and finding one line for it in their own
queue at the next session start. They cannot close it back: a close by the
recipient is refused by the listener and marked by the scan instead. When its
author closes it, the line is marked and the next check stops reporting it.

A person can see the skill is one file by opening the folder: it holds
`SKILL.md`, `COMMUNICATE-ISSUE-FORMAT.md`, and `agents/openai.yaml`, and the
commands for sending and answering are both in `SKILL.md`.

A person can see the rule is installed by finding the same bytes at
`weave-your-work/setup/rules/rules-pending-communications.md` and
`.agents/rules/rules-pending-communications.md`, and no rule telling a session
to wait for a person before acting on a queued entry.

The issue tests pass with the fake `gh`.

## Out of Scope

- Removing `category` or `kind` from the front matter.
- A direction field on the queue line, or a second list. One mixed list.
- Handling `issue_comment`. Comments still do not enter the queue.
- Handling `reopened`. A reopened issue is recovered by the startup scan.
- A webhook subscription change. `issues` is still the only event.
- The close rule itself. Only the issue's author closes it, as before.
- Reading the queue from inside the skill. The session rule reads it.
- The listener copy installed in a checkout.

## Further Notes

The mixed list is deliberate: knowing an issue exists is enough, and the issue
itself is one command away. The line staying until the issue closes is also
deliberate: it is how the sender checks on the other side without asking.

The sender's line and the recipient's line are not the same observation of the
same event. The recipient gets a notification and a queue line. The sender gets
a queue line that stays until the thread closes, which is the closest thing to a
completion signal that exists without a new status. If a person later wants
"handled" distinguished from "still open", that needs a status, and the format
has none.

Removing the record id is not the same as removing the record. A message can
still be about a spec or a ticket; it just says so in prose. What goes is the
promise that the answer is delivered to a file, because the two checkouts do not
share one.
