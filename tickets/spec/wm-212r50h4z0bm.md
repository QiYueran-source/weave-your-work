## Problem Statement

The queue records only the issues assigned to this machine's owner. A person
who opens an issue and assigns it to another owner gets nothing in their own
queue, so the sender has no local signal about whether the other side has
handled it. The recipient's session is reminded; the sender's is not.

The asymmetry is not a bug in any one part: `queueIssue` in `listener.mjs`
rejects every issue whose assignee is not this machine's owner (line 503),
which is the same rule that keeps strangers out. The rule is right for
strangers and wrong for the sender, who is a party to the thread.

The user has decided both sides should see an issue's state: a queue that
holds every open issue its owner is party to, whether they sent it or
received it. Closing stays with the person who opened the issue.

## Solution

Widen one filter: an issue is queued when either its author or its assignee is
this machine's owner. Everything else about the queue stays as it is.

An issue stays in the queue for as long as it is open. A closed issue keeps
its line, marked, and is no longer reported. The sender therefore sees a
thread leave the report exactly when it closes, which is the signal they
were missing.

Closing does not move. A close by anyone other than the issue's author is
still refused by the listener, and the startup scan still marks a line whose
issue GitHub no longer lists as open. That fallback is what covers a thread
the recipient could not close, or one closed while no listener was running.

## User Stories

1. As a person who sends an issue to another owner, I want it in my own
   queue until it closes, so that I can see whether the other side has
   handled it without opening GitHub.
2. As a person who receives an issue, I want it in my queue as before, so
   that nothing about receiving changes.
3. As a person reading the queue at session start, I want one list of
   everything open that involves me, so that I do not have to look in two
   places.
4. As a person who closed an issue I sent, I want its line marked and gone
   from the report, so that the list stays about work still outstanding.
5. As the owner of a repository with strangers in it, I want an issue that
   neither I sent nor am assigned to to stay out of my queue, so that widening
   the rule does not turn the queue into every issue in the project.

## Implementation Decisions

**One predicate replaces one comparison.** `queueIssue` becomes
`const involved = from === machineOwner || to === machineOwner`, and the
skip message names both owners:
`Skipped <label>: <from> to <to> does not involve <machineOwner>`.

**The queue line does not change shape.** `url`, `from`, `to`, `owner`,
`title`, `received`, `closed_at` stay. `owner` continues to hold the
assignee's owner name; it is the assignee, not this machine, that the field
names.

**One URL is one line.** `append` already deduplicates on URL, so an issue the
owner both sent and was assigned is still one line.

**The startup log says what the listener now does.** `queueing messages
assigned to <owner>` becomes `queueing issues involving <owner>`.

**The report does not gain a direction.** A sent and a received issue look
alike in `check-pending.mjs`'s output. The person reads the queue for "what is
open that I am part of" and opens the issue on GitHub for anything more.

**The roster still gates both sides.** An issue whose author or assignee is
outside the roster is still dropped, and an issue whose author is a roster
member but whose assignee is not is still dropped. Widening the predicate
widens only which roster members count, never whether the roster counts.

## Testing Decisions

**What a good test is here.** The existing shape: a real listener against a
temporary checkout, an event over HTTP, and the queue file read back. The
fake `gh` on `PATH` answers the single-issue read as it already does.

**What is tested.**

- An issue this machine's owner opened and assigned to another roster
  member queues one line, with `from` this owner and `to` the other.
- An issue assigned to this machine's owner queues as before.
- An issue whose author and assignee are both other roster members adds no
  line.
- An issue from outside the roster still adds no line, whichever end the
  stranger is on.
- The startup scan queues an open issue the owner sent and the queue lacks.
- A line for an issue the owner sent is marked closed by the scan when GitHub
  no longer lists it open, and the listener's own close event still refuses a
  closer who is not the author.

**What changes in the existing tests.** `test-catchup.mjs:290` asserts that an
issue assigned to bob is not queued on alice's machine. The assertion narrows
to "an issue whose two parties are other members is not queued", and a case
for alice's own outgoing issue is added beside it. `test-security.mjs:543`
keeps its stranger case unchanged and gains the outgoing case.

## Acceptance

A person can see it work by opening an issue as their own account, assigning
it to another roster member, and finding one line for it in their own queue at
the next session start. They cannot close it back — a close by the recipient
is refused by the listener and marked by the scan instead — and when it is
closed by its author the line is marked and the next check stops reporting it.

The issue tests pass with the fake `gh`.

## Out of Scope

- A direction field on the queue line, or a second list. One mixed list.
- Removing `tickets` or `category` from the message front matter. That is a
  separate question and is not decided here.
- Handling `issue_comment`. Comments still do not enter the queue.
- Handling `reopened`. A reopened issue is recovered by the startup scan, not
  by an event.
- A webhook subscription change. `issues` is still the only event.
- The close rule itself. Only the issue's author closes it, as before.
- The listener copy installed in a checkout. It is reinstalled from the
  install guide; it is not edited in place.

## Further Notes

The user's two answers are recorded here because they are the parts a later
reader would otherwise second-guess. The mixed list is deliberate: knowing
an issue exists is enough, and the issue itself is one command away. The
line staying until the issue closes is also deliberate: it is how the
sender checks on the other side without asking.

The sender's line and the recipient's line are not the same observation of
the same event. The recipient gets a notification and a queue line. The sender
gets a queue line that stays until the thread closes, which is the closest
thing to a completion signal that exists without a new status. If a person
later wants "handled" distinguished from "still open", that needs a status,
and the format has none.
