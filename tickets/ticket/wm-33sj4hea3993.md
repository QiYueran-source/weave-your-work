## Action

In the merge, order the terms inside each group by `updated_at`, newest first. The groups themselves keep the order they are discovered in.

This is the only behaviour the spec changes. It answers a reader's question that the current view cannot: what has the project settled most recently.

## Acceptance signal

Two checks, read off the generated view:

- Given three terms in one group whose `updated_at` values are in ascending order, the view lists them in descending order.
- A term with no group still lands under the default heading, and ordering applies there as well.

## Result

Done. The merge sorts each group's terms by `updated_at` before writing the section. A temporary project with three terms in one group, stamped `01:00`, `02:00`, and `03:00`, renders `丙`, `乙`, `甲`: newest first.

One note on how it was checked. A first attempt wrote three terms in a row and slept between them, and the result looked wrong. Reading the source showed the timestamps themselves were out of order, not the sort: two writes landed in the same second and the third landed a second earlier. The check was rerun with fixed timestamps in the source file, which is what the acceptance signal asks for.
