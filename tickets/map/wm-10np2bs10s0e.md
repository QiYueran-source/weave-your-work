## Target

A stranger installs this set from the public repo with one command and gets exactly the skills under `weave-your-work/`, and every change that lands reaches a tagged release with a changelog nobody wrote by hand.

Why: the repo is public and already indexed by skills.sh, but the command that page prints installs 39 skills that are all copies of matt's set and none of this set's own. The repo also carries no README, no license, and no version, so a reader who arrives has nothing to read and no way to tell what changed between releases.

## Acceptance direction

On a machine that has never seen the repo, `npx skills add qiyueran-source/weave-your-work` lists exactly the skills under `weave-your-work/`, with nothing sourced from `.agents/skills/` and no `Skipped` line; and the public repo carries a tag whose release page shows a changelog naming what changed.

Review point: that install log, read against the directory list under `weave-your-work/`; the newest tag's release page; the repo front page, read for the install command, the license, and one paragraph saying what the set does.

## Decisions so far

- The `skills` CLI searches a fixed set of containers: a `SKILL.md` at the repo root, `skills/`, and agent project directories such as `.agents/skills/`, each walked three levels deep. A `skills.sh.json` at the repo root carrying `{"paths":[...]}` adds directories to that search. `weave-your-work/` is none of them, so root-level discovery never looks inside it on its own. (verified 2026-11-10 by running the cached CLI against this repo, skills 1.7.6)
- The exact command skills.sh prints, `npx skills add qiyueran-source/weave-your-work`, returns 39 skills, all of them from `.agents/skills/`. Aiming at the subpath instead, `npx skills add qiyueran-source/weave-your-work/weave-your-work`, returns 15 against `origin/main` and 19 against the local tree; the four missing ones are committed here and not pushed.
- The layout is `.agents/matt-skills/` plus a `skills.sh.json` at the repo root carrying `{"paths": ["./weave-your-work"]}`. The vendored reference set stays in the repository and stays readable; `.agents/skills/` becomes the install target and is gitignored, so a clone starts without it and the first install fills it. Measured on a fresh clone of that layout: exactly 19 skills, no `Skipped` line. (user confirmed 2026-11-10)
- The vendored tree sits at `.agents/matt-skills/` rather than `.agents/skills/` because only the latter is a discovery container. Renaming alone is not enough: measured, a renamed tree with no `skills.sh.json` returns 59 skills, because the fallback walk still finds every `SKILL.md` in the repo. The config file is what narrows discovery to `weave-your-work/`, and the rename is what keeps the reference set out of the walk. Both halves are required.
- `.agents/skills/issue` stops being tracked. It is an installed copy of `weave-your-work/issue`, it is regenerated by an install, and it carries this project's roster, which the source copy does not, so tracking it recorded a copy rather than a source.
- The skill ships a roster template, not a filled-in roster, and this project's roster moves out of the install target and stays committed. The two files are different artifacts: one is the shape a new project fills in, the other is this project's people data. A stranger who installs the set currently receives `frank = "QiYueran-source"`, and `skills add --copy` deletes that file before writing, so keeping the real roster there both publishes it and loses it on update. Owning task: [Separate the roster template from this project's roster](../task/wm-ssfcjp9hxbxh.md). (user confirmed 2026-11-10)
- The license is Apache-2.0. (user confirmed 2026-11-10)
- `npx skills add owner/repo` does not download from GitHub releases. For any owner outside a four-name allowlist (`vercel`, `vercel-labs`, `heygen-com`, `remotion-dev`) the CLI runs `git clone --depth 1` and reads the working tree; a tag is used only when the source names a ref, as in `owner/repo#v1.2.3`. A release pipeline exists so a reader can see what changed, not because installs need it. (verified 2026-11-10 in the CLI source)
- Matt has no version of this problem to copy: his real skills live in `skills/` at the repo root, which is a native discovery container, and he commits no `.agents/skills/` at all. `scripts/link-skills.sh` symlinks them into `~/.claude/skills` and `~/.agents/skills`, outside the repo, so his installed copies never enter version control. This repo differs because it develops its skills in `weave-your-work/` and keeps a reference set inside `.agents/`.
- Matt's release model is a private package plus changesets with `privatePackages: {version: true, tag: true}`, driven by one `release.yml` on push to `main` that runs `changesets/action@v1` with `version: npm run version` and `publish: npx changeset tag`. Merging the version PR is what writes the tag and the GitHub release; tags are annotated and carry `v1.3.2`, not the bare version.
- Matt's CI does not verify skills at all: three workflows (`release`, `triage-label`, `needs-info`) and no lint, test, or front-matter check. A malformed `SKILL.md` reaches `main` and is noticed only when an install skips it with `YAML parse error`, which exits 0 and leaves the skill uninstalled. Recorded here as a gap, not as a model to follow.

## Not yet specified

- Whether a release also publishes to npm, which needs a package name and a scope. Installs work from GitHub without it.
- Whether `skill-creator` and `talk-like-a-human` ship with the set or stay development-only. The CLI skips both today because the lock names them, not because the repo excludes them.
- Which checks the verification workflow runs beyond discovery, and whether it blocks a merge or only reports.
- `GLOSSARY.md` is gitignored while some skills refer to a shared glossary; whether it ships is unsettled.
- Where this project's roster lives once it leaves `.agents/skills/`: `.agents/issue-handles.toml`, or back to `.waymark/handles.toml` where it lived before 2026-11-09.

## Out of scope

- The Claude Code plugin marketplace and `plugin.json`, which is matt's second distribution channel.
- A Codex plugin manifest.
- Publishing to any other registry or marketplace.
- A docs site or landing page.
