## Target

Deliver the issue skill: carry a **communicate issue** between team members on GitHub, route it to the person it names, land the decisions that change local work, and keep the ticket as the record. The skill ships a listener: a smee webhook receives the issue, the listener queues it for the recipient, and the next session surfaces it.

Why: remote communication and the local tracker are separate surfaces. A message should reach the right person without the ticket tree waiting for a merge, and only what changes local work should come back.

## Acceptance direction

`weave-your-work/issue/` holds `SKILL.md`, `communicate-issue.md`, `usage.md`, and `bundle/` with `setup.md`, `rules/`, and `tools/`. A communicate issue filed on a remote repo with the agreed frontmatter reaches the recipient through smee; the session-start rule surfaces it with the count and titles; a decision that changes a map or task lands there; a rejection lands in the map's `Out of scope`; the issue closes. The bundled listener connects to GitHub only.

Review point: check the frontmatter schema, the single-recipient routing, the queue and session rule, the local-artifact test, and the listener's offline catch-up.

## Decisions so far

- A **communicate issue** is a normal GitHub issue whose body starts with YAML frontmatter; the frontmatter marks it, so no label or title prefix is needed. (user confirmed, 2026-11-08)
- The frontmatter carries `kind: communicate`, `to` (one or more remote handles), `tickets` (one or more waymark ids; the first is the primary and the title carries it), and `from` (the waymark owner sending). The body opens with `@handle` for the platform notification, then the ask, the context, and how to reply. (user confirmed, 2026-11-08)
- One issue can address several people and list several tickets; each `to` gets a queue entry and the thread is shared. The update caller's one-issue-per-affected-owner rule stays for decisions that differ. (user confirmed, 2026-11-08)
- An issue lands locally only when it produces a local artifact: an accepted change to a map or task, or a rejection recorded in the map's `Out of scope`. Discussion without an artifact stays remote. Matt's triage uses the same test through its brief, notes, and out-of-scope outputs; its label state machine is not copied. (user confirmed, 2026-11-08)
- The listener is part of the issue skill: a smee.io channel receives the GitHub webhook, a local listener parses the frontmatter, routes by `to`, and appends to the pending queue. The queue is surfaced at the next session; nothing acts on it automatically. (user confirmed, 2026-11-08)
- The queue lives in a separate ignored directory; its path is configured in the shared, tracked handles file. The previous location, `.waymark/handles.toml`, is superseded by the setup decision below.
- The handles file records the whole team by mapping waymark owners to remote handles, and the listener reverse-maps the handle to the owner. A missing owner or account means ask; never guess. Operator, git user, and issue author may differ, and `from` plus the ticket identify the sender. ~~One table per platform (`[handles.github]`, `[handles.gitee]`)~~ and ~~the author is ignored~~ were superseded on 2026-11-09: the table is one flat `[handles]`, and the author is checked against it as a roster rather than ignored. (user confirmed, 2026-11-08; amended 2026-11-09)
- Put the project-specific handles file in the installed issue skill's `bundle/tools/`, not `.waymark/`. Issue setup asks the person responsible for the owner-to-handle mappings and creates the file on first setup; later setup preserves it. Because `skills add --copy` deletes the destination on update, back up the file before updating and restore it afterward. The installed skill and the file are committed with the project. (user confirmed, 2026-11-09)
- The smee setup is `bundle/setup.md`; the setup skill copies `bundle/rules/*.md` into `.agents/rules/`. The session rule asks the agent to check pending once at session start and wait for the person before acting. A read-only Node checker provides count, titles, and links; a supported harness may optionally run it as a session-start hook, adapted and verified for that harness. The rule remains the fallback. No file watcher, polling, or active-session notification is required. (user confirmed, 2026-11-09)
- For convenient internal use, smee delivery does not require a webhook secret by default. Treat queued messages as unauthenticated reminders, not proof of sender identity; the channel URL must be kept private and an agent waits for the person before acting. Encode new entries as structured JSON list items and keep reading legacy entries without rewriting the queue. (user confirmed, 2026-11-09)
- On listener startup, connect the live stream and scan the current project's remote repo for open communicate issues, filtering frontmatter and deduplicating queue entries. This replaces mention search; do not poll or scan other repositories. Closed issues and later disconnections remain outside this catch-up. (user confirmed, 2026-11-09)
- The update skill's archive hand-over stays the first caller: one issue per affected owner, carrying the relation, the replacement id, and the decision. (user confirmed earlier; recorded in the Update map)
- The skill is model-invocable: a run that needs to file, read, or land a communicate issue loads it; a person can invoke it too. (user confirmed earlier)
- The listener queues a message only when the issue's author is a login in `handles.toml`, on both the webhook path and the startup scan. This is a roster, not authentication: signature verification cannot work through smee, which re-serializes the JSON, so the author field travels in the same unverified payload. (user confirmed, 2026-11-09)
- Setup reads the channel, webhook, service, and handles file back with `gh` before creating anything and creates only when the read is empty. One channel per repository, since smee fans each event out to every connected client. No `.env.example`: the real file lives outside the repository and `setup.md` is its one description. (user confirmed, 2026-11-09)
- One `usage.md` replaces the two platform references and the skill supports GitHub only. The five operations are contracts with exact commands only for this skill's own tools; `gh` is specified by capability, not syntax. `usage.md` closes with the other hosts and what a fork would change, so the limit is stated where a reader looks for it. The listener stays a single process with its GitHub-specific code in two named functions, and `handles.toml` is a flat `[handles]` table. (user confirmed, 2026-11-09)

## Out of scope

- The full issue triage state machine; triage remains its own skill for incoming work issues.
- A second host. GitHub is the only host; Gitee's write path was deferred and is not built. Another host needs its own event and listing code, its own setup, and its own handle table before the skill can claim it.
- Acting on a queued issue without the person asking.
