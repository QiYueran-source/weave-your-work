## Target

Design the issue skill: file issues on a remote repository, view and reply to them, and write decisions formed in discussion back to the corresponding waymark items, so the team communicates in real time without touching local state. Follows the draft's division (section 6): remote issues are for immediate communication, waymark is the single local source of truth.

## Acceptance direction

`weave-your-work/issue/` exists with `SKILL.md` and one reference per platform, `github.md` and `gitee.md`. A reader can take a ticket through all five actions — file, read, reply, land the decision, close — on GitHub. Every GitHub command has been run against a scratch repository, and the skill installs with `npx skills add` without a YAML parse error. Gitee's write path is an unexercised path for the end-to-end batch; its reads and write endpoints are checked.

Review point: Check the five actions against the three callers — update's archive hand-over, a task's human step, and a foreign parent's reopen request — and check that no rule writes a ticket the run does not own.

## Notes

- Category: communication. Answers "are we aligned, how do we talk remotely".
- Trigger: model-invocable. A run loads it when a ticket needs to tell another owner something, or when a person wants to read and answer a thread.
- Delivery location: weave-your-work/issue/.
- Platforms: GitHub through the `gh` CLI, Gitee through its REST API v5. GitHub's five actions are verified on a private scratch repository (`gh` 2.103.3, authenticated). Gitee's read path and write endpoints are checked; its write path is deferred to the end-to-end batch (user, 2026-11-08).
- Borrowed from: .inbox/work-methods/domain-and-conventions.md section 6 (GitHub/Gitee for immediate communication; discussion is not copied locally; only decisions formed are written back to the work item by the entitled owner).

## Decisions so far

- issue is for remote real-time communication; waymark is the single local source of truth (draft section 6 direction, not finally confirmed).
- The update skill is the first caller and sets a floor for the shape: it files one issue per affected owner after an archive, and the issue must name the relation that was removed and the id that replaced the node, so the owner can re-point the edge or accept the outcome. An issue that only says "something changed" fails this caller. (user confirmed; recorded in Update skill, wm-9sfmaphskg0c)
- Both GitHub and Gitee are supported: GitHub through `gh`, Gitee through its REST API v5. (user confirmed)
- The skill is model-invocable. A run that needs to tell another owner something, or to read an answer it is waiting on, loads it; a person can also invoke it. Filing one issue is bounded work, unlike the two execute skills, which are user-invoked because they spend an unbounded number of subagents. (user confirmed)
- Gitee is deferred for now: the Gitee reference stays in the skill, its reads and write endpoints are checked, and its write path is an unexercised path for the end-to-end batch. GitHub is the acceptance platform until then. (user confirmed, 2026-11-08)
- The skill is a message channel tied to a ticket: file, read, reply, land, close. It carries no triage labels, no queue, and no ticket creation from an issue; an accepted proposal goes through split. (agent decision, revisable)
- The title carries the id of the ticket that will record the answer, and the action the recipient must take; the body carries the recipient, the ticket or tickets, the ask, and how to reply. No labels by default; the ticket id in the title is how the remote side and the local side find each other. (agent decision, revisable)
- The issue opens with the ask, then the context, then how to reply. A known handle is used twice: mentioned in the body and set as the assignee, because the mention notifies and the assignment queues the issue. An unknown handle or an account-less recipient is told out of band, and the issue remains the record; a reply-by line is optional for an urgent ask, and nothing polls. (agent decision, revisable, 2026-11-08)
- An answer is a decision when it changes a ticket's text, status, or relations, or settles a fact the ticket already cites. Agreement, thanks, scheduling, and options that lost stay in the thread and are not copied locally. (agent decision, revisable)
- A decision is written into the ticket that owns it: a map's `Decisions so far`, a task's affected section, or `Result` for a person's answer, with the issue URL as its source. This skill does not use the comment category; whether that category stays belongs to the execution map. (agent decision, revisable)
- No triage state machine: the skill moves a message between two people and does not sort incoming work. An issue with no ticket behind it is read and answered; when an owner accepts it, split creates the ticket and the closing comment links it. (agent decision, revisable)
- A triage outcome lands as a decision, not a state machine: an accepted proposal becomes a ticket through split and carries the issue URL; a rejected one goes into the map's `Out of scope` with the reason and the URL; `needs info` lands nothing. The map's owner writes it. (agent decision, revisable, 2026-11-08)
- A remote handle comes from `.waymark/handles.toml`, in the table for the platform, after the account is verified; a missing table, owner, or account means ask, and the waymark name is never guessed as a login. (agent decision, revisable, 2026-11-08)
