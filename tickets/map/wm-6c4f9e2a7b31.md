## Target

Define how every section and entry in a map body is written, including Target, Acceptance direction, Decisions so far, Not yet specified, Out of scope, and Review, so the map has a consistent content model that map, explore, split, and review can share.

Why: naming the sections is not enough. Without entry formats, each map can express the same kind of information differently, and the other execution skills cannot reliably read or accept it.

## Acceptance direction

The `body.md` reference exists under `weave-your-work/map/`. It defines the purpose, entry shape, required information, and routing rule for every section, `Review` included. It includes examples for a target, decision, fog item, out-of-scope item, and an invalidated verdict, and it distinguishes map body rules from map workflow rules.

Review point: read `body.md` end to end — every section states its purpose, entry shape, and a usable example; the four fog forms and the four Review verdicts each appear; the file states no workflow rule and defines no field; the whole-map example is a body a reader can write from.

## Decisions so far

- The map skill has a separate `body.md` reference for content rules; `SKILL.md` keeps the map workflow and points to the reference. (user confirmed, 2026-11-09)
- Map owns the definition of fog because fog is content in the `Not yet specified` section. Explore owns fog classification, routing, and landing. (user confirmed, 2026-11-09)
- `Not yet specified` may contain several kinds of unclear content, including assumptions, facts to establish, decisions to make, and goals to clarify. These are entry types within one section, not separate top-level sections. The types are not a closed list; a map may use another type when needed. Every built-in fog type states why resolving it matters: ordinary types use `Why it matters`, while `Assumption` uses the more specific `If wrong` and does not repeat a second impact field. A custom type may define its own fields and does not have to use `Why it matters`. `body.md` defines the shared entry model and the common formats; explore determines how to classify and resolve each entry. Source: user confirmation.
- Target follows this format:

  ```md
  ## Target

  [What should be true when this map succeeds.]

  Why: [Why this target is worth pursuing.]
  ```

  It states one expected outcome, does not name an implementation solution, and keeps deliberate exclusions in `Out of scope` rather than a separate `Boundaries` entry. Source: user confirmation.

When split creates a child ticket, the split skill sets its parent and adds the link to Children.~~ Superseded on 2026-11-08: the `## Children` section is removed from the map body. - What the removed index used to give a reader — one line per child saying what it is for — is now read from `waymark tree --root <id>` for the shape and from each child's own Target for the meaning. A parent map whose children cannot be understood without an index has not stated its split in `Target`. Source: user confirmation.
- Decisions so far records settled rules or directions that affect the current map. Each entry holds one decision in its concrete form, and includes a source. Unsettled content stays in Not yet specified; rejected alternatives and discussion history belong in a testimony, not here. Any body item may link a testimony as the discussion it came from. Source: user confirmation.
- Fog entry forms use these templates:

  ```md
  - Assumption: [What we currently believe.]
    If wrong: [What target, acceptance direction, child, or scope decision could change.]
  ```

  ```md
  - Fact to establish: [What fact is missing.]
    Why it matters: [What depends on this fact.]
  ```

  ```md
  - Decision to make: [What must be decided.]
    Why it matters: [What depends on this decision.]
  ```

  ```md
  - Goal to clarify: [What part of the target is unclear.]
    Why it matters: [What changes if the goal is clarified differently.]
  ```

  `Assumption` uses `If wrong`; the other built-in forms use `Why it matters`. A custom form may use other fields. A resolved goal updates `Target` rather than directly becoming a task. Source: user confirmation.
- A resolved fog entry remains in `Not yet specified` with the original entry struck through and a `Resolved:` line pointing to its result. Irrelevant fog may be deleted. Source: user confirmation.
- Out of scope holds items that are clearly not being done, each with a reason. An item that may be done later is not an exclusion; it stays in Not yet specified until it is decided. Source: user confirmation.
- The `body.md` reference organizes each section with purpose, format, and a directly usable example; each fog entry type gets its own subsection covering when to use it, its format, and an example. `body.md` defines content rules only; map workflow rules belong in the Map operating procedure reference. Source: user confirmation.

Weave logs are shared evidence records, not tickets.~~ Superseded on 2026-11-08: a testimony holds only grill discussion; where other material lives is still open (see [Testimony records](wm-31f6a2c9d840.md)). Source: user confirmation.
- Acceptance direction uses a default or a specific result, with a review point:

  ```md
  ## Acceptance direction

  [Specific observable result, or the default below when no clear destination can be stated.]

  All children are complete and no further children are needed.

  Review point: [Specific items the reviewer checks against the target and acceptance direction.]
  ```

  The default is `All children are complete and no further children are needed.` A map may add a specific observable result when its target can be checked directly. The review point states what evidence or state the reviewer checks; it is required whether the map uses the default or a specific result. Source: user confirmation.
- The map body keeps six sections. `Review` records a verdict and its evidence in `body.md`; when a verdict is invalidated, and who disposes of it, stay with `map-review` and `update`. A whole-ticket example may display front matter because that is how waymark stores a ticket, but the file defines no field rule. (user confirmed, 2026-11-09)
- Acceptance direction stays concise and carries the goal, not the checklist. The review point carries the detail: it must be written as checkable items (what state to look for, what evidence to see), specific enough that the reviewer does not guess. A specific result must be observable and verifiable ("a signal appears, a state is reached"), not "best effort". When the review point cannot be made checkable, the goal itself is not yet clear; the fog goes back to explore, it is not forced through review. Source: user confirmation.
