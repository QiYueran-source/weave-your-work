## Target

Define how every section and entry in a map body is written, including Target, Acceptance direction, Children, Decisions so far, Not yet specified, and Out of scope, so the map has a consistent content model that map, explore, split, and review can share.

Why: naming six sections is not enough. Without entry formats, each map can express the same kind of information differently, and the other execution skills cannot reliably read or accept it.

## Acceptance direction

The `body.md` reference exists under `weave-your-work/map/`. It defines the purpose, entry shape, required information, and routing rule for every section. It includes examples for a target, decision, fog item, and out-of-scope item. A reader can write the worked example map from the reference without inventing a format, and the reference distinguishes map body rules from map workflow rules.

## Decisions so far

- The map skill has a separate `body.md` reference for content rules; `SKILL.md` keeps the map workflow and points to the reference.
- Map owns the definition of fog because fog is content in the `Not yet specified` section. Explore owns fog classification, routing, and landing.
- `Not yet specified` may contain several kinds of unclear content, including assumptions, facts to establish, decisions to make, and goals to clarify. These are entry types within one section, not separate top-level sections. The types are not a closed list; a map may use another type when needed. Every built-in fog type states why resolving it matters: ordinary types use `Why it matters`, while `Assumption` uses the more specific `If wrong` and does not repeat a second impact field. A custom type may define its own fields and does not have to use `Why it matters`. `body.md` defines the shared entry model and the common formats; explore determines how to classify and resolve each entry. Source: user confirmation.
- Target follows this format:

  ```md
  ## Target

  [What should be true when this map succeeds.]

  Why: [Why this target is worth pursuing.]
  ```

  It states one expected outcome, does not name an implementation solution, and keeps deliberate exclusions in `Out of scope` rather than a separate `Boundaries` entry. Source: user confirmation.
- Children uses a simple list of links to existing child tickets; it does not repeat refinement descriptions because readers can inspect each child node for its details. Children may contain tasks or submaps. When [split](tickets/map/wm-3nhrhmds8rqd.md) creates a child ticket, the split skill sets its parent and adds the link to Children. Source: user confirmation.
- Decisions so far records settled rules or directions that affect the current map. Each entry uses its concrete form, and includes a source. Unsettled content stays in Not yet specified; rejected alternatives and discussion history belong in weave logs, not here. Any body item may link a weave log as its key evidence. Source: user confirmation.
- Fog entry forms use these templates:

  ```md
  - Assumption: [What we currently believe.]
    If wrong: [What target, acceptance direction, child, or scope decision could change.]
  ```

  ```md
  - Fact to establish: [What fact is missing.]
    Why it matters: [What depends on this fact.]
  ```

  ```md
  - Decision to make: [What must be decided.]
    Why it matters: [What depends on this decision.]
  ```

  ```md
  - Goal to clarify: [What part of the target is unclear.]
    Why it matters: [What changes if the goal is clarified differently.]
  ```

  `Assumption` uses `If wrong`; the other built-in forms use `Why it matters`. A custom form may use other fields. A resolved goal updates `Target` rather than directly becoming a task. Source: user confirmation.
- A resolved fog entry remains in `Not yet specified` with the original entry struck through and a `Resolved:` line pointing to its result. Irrelevant fog may be deleted. Source: user confirmation.
- Out of scope holds items that are clearly not being done, each with a reason. An item that may be done later is not an exclusion; it stays in Not yet specified until it is decided. Source: user confirmation.
- The `body.md` reference organizes each section with purpose, format, and a directly usable example; each fog entry type gets its own subsection covering when to use it, its format, and an example. `body.md` defines content rules only; map workflow rules belong in the Map operating procedure reference. Source: user confirmation.
- A map body may include short log entries for concise facts or observations. Longer records use a separate Markdown file under the root `weave-logs/` directory, linked from the relevant body entry. Weave logs are shared evidence records, not tickets. Source: user confirmation.
- Acceptance direction uses a default or a specific result, with a review point:

  ```md
  ## Acceptance direction

  [Specific observable result, or the default below when no clear destination can be stated.]

  All children are complete and no further children are needed.

  Review point: [Specific items the reviewer checks against the target and acceptance direction.]
  ```

  The default is `All children are complete and no further children are needed.` A map may add a specific observable result when its target can be checked directly. The review point states what evidence or state the reviewer checks; it is required whether the map uses the default or a specific result. Source: user confirmation.

## Not yet specified

- Assumption: Children should be a readable mirror of the waymark parent relation and should not carry dependency order. If wrong: the body may disagree with the target tree or imply an execution order that belongs on dependency edges.
- Assumption: each Decisions so far entry should contain one decision and its source. If wrong: settled rules become hard to verify and the map turns into a second copy of its child tickets.
- Assumption: `body.md` should define content rules while `SKILL.md` defines workflow rules. If wrong: the map skill will either repeat body rules across workflows or leave the writing contract implicit.
- Assumption: the reference needs a worked example and a verification approach. If wrong: the format may look complete but still require readers to invent how to apply it.
## Out of scope

- How a map is created, split, explored, reviewed, or advanced.
- The task body format and task lifecycle.
- Product-specific validation methods.
